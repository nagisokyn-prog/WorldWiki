# 🗺️ Спецификация: Мульти-персонажный Навигатор (Multi-Entity Journey)

Текущий навигатор сцен (`CharacterJourney`) заточен под одного персонажа. Идея наложения и отслеживания сразу нескольких персонажей открывает огромный потенциал для анализа сюжета, динамики отношений и пересечения сюжетных арок.

Ниже представлены концепции того, как это можно реализовать архитектурно и визуально, оставаясь в рамках нашего дизайн-кода.

---

## 🎨 1. Визуальные Концепции (UX/UI)

### Концепция А: Объединенное дерево (Union Mode)
Самый естественный способ расширить текущий UI — позволить выбрать несколько персонажей (например, через тэги/чипсы в селекторе) и слить их путешествия в одно дерево.

**Как это выглядит в интерфейсе (Narrative / Arcs Mode):**
Сцена выводится один раз (как один узел дерева), но внутри нее показываются бейджи или аватарки всех выбранных персонажей, которые в ней участвуют. 

```text
[Глава 5: Встреча в таверне]
  ├── 🟢 Сонечка [Арка: Грех и падение]
  └── 🔵 Макс [Арка: Искупление]
```
*Таким образом, мы видим пересечение конкретных героев и их сюжетных арок в рамках одной сцены.*

### Концепция Б: Строгое пересечение (Intersection Mode)
Режим "Только совместные сцены" (Toggle "Show only intersections").
Дерево отфильтровывается и оставляет **только те сцены, где присутствуют ВСЕ выбранные персонажи**.
- Идеально для отслеживания динамики отношений (Relationship Tracking) между двумя героями.
- Сразу видно, когда они встретились, как долго не виделись (можно вычислять и выводить плашку "⏳ Прошло 3 года с прошлой встречи"), и в каких фазах арок они находятся при взаимодействии.

### Концепция В: Параллельная Хронология (Swimlanes / Gantt)
В режиме `CHRONOLOGY` (когда важна абсолютная временная шкала `m_abs`, а не порядок глав), интерфейс делится на вертикальные колонки (Swimlanes) для каждого персонажа.
- Совместные сцены образуют единый "мост" или блок, растянутый на обе колонки.
- События, в которых участвует только один герой, остаются только в его колонке.

## ⚙️ 2. Архитектурная Реализация (Frontend)

Для реализации не обязательно менять бэкенд и ломать `fn::get_character_journey`. Всю магию слияния и оркестрации запросов можно сделать на уровне `useCharacterJourney` и его хуков.

### 2.1 Изменение стейта (Store/Hook)
Вместо одного `currentEntityId: string` мы вводим массив `selectedEntityIds: string[]`.

```typescript
// useCharacterJourney.ts
const selectedEntityIds = ref<string[]>([]);
// Храним данные по всем выбранным ID
const multiData = ref<Record<string, CharacterJourneyData>>({});

const loadJourneys = async () => {
  isLoading.value = true;
  // Параллельный запрос к бэкенду для каждого персонажа
  const fetchPromises = selectedEntityIds.value.map(id => getCharacterJourney(projectId, id));
  const results = await Promise.all(fetchPromises);
  
  // Сохраняем данные по каждому ID
  results.forEach((data, index) => {
    const id = selectedEntityIds.value[index];
    multiData.value[id] = data;
  });
  isLoading.value = false;
};
```

### 2.2 Хук слияния (useJourneyItemsBuilder.ts)
Обновляем билдер для склейки элементов.

**Логика склейки (GroupBy Chapter/Event):**
1. Проходим по всем `appearances` всех персонажей из `multiData`.
2. Группируем их по `chapter_id`.
3. Формируем единый `JourneyTimelineItem` для сцены, добавляя в него массив участников (`presentEntities`):

```typescript
export interface JourneyTimelineItem {
  id: string;
  type: 'appearance' | 'event' | 'relation_change';
  chapter_id?: string;
  // ... базовые поля ...
  
  // Новое поле для мульти-режима
  presentEntities: Array<{
    entityId: string;
    entityName: string;
    role?: string;
    arcs?: BoundArc[]; // Текущие арки именно этого персонажа в сцене
  }>;
}
```

### 2.3 Рендер в компоненте (UI)
- **Шапка**: Добавляем EntityPicker с поддержкой мульти-селекта (чипсы или чекбоксы).
- **Карточка дерева**: В `JourneyTimelineItem` (или аналоге) мы проверяем массив `presentEntities`. Если там больше одного элемента, мы рендерим мини-список или горизонтальный стэк имен с цветами их арок.

## 🚀 3. Пошаговый План Внедрения (Roadmap)

Если эта идея откликается, мы можем внедрять её итеративно:

1. **Шаг 1: Поддержка мульти-селекта**
   - Перевод UI селектора на выбор нескольких сущностей (массив `selectedEntityIds`).
   - Реализация `Promise.all` для загрузки нескольких journey-датасетов.
2. **Шаг 2: Группировка (Слияние узлов)**
   - Обновление алгоритма в `useJourneyItemsBuilder` для группировки одинаковых сцен/глав в один узел дерева.
   - Добавление `presentEntities` в доменную модель.
3. **Шаг 3: Обновление UI карточек**
   - CSS и верстка для красивого отображения нескольких персонажей в одном блоке сцены (тэги, цвета арок).
4. **Шаг 4: Фильтр "Пересечения" (Intersection)**
   - Добавление UI-свитчера "Только совместные сцены", который фильтрует дерево по условию `presentEntities.length === selectedEntityIds.length`.
