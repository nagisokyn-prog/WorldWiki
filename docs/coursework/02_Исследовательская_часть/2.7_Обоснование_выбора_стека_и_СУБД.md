## 2.7. Обоснование выбора инструментов и платформы для разработки

### 2.7.1. Обоснование выбора системы управления базами данных (СУБД)
Выбор СУБД является ключевым архитектурным решением, определяющим надежность, автономность и производительность проектируемой системы. В таблице 2.3 приведен сравнительный анализ различных классов СУБД применительно к специфике требований АС «WorldWiki».

Таблица 2.3 — Сравнительный анализ альтернативных СУБД и хранилищ данных

| Класс СУБД / Хранилища | Достоинства | Ограничения применительно к архитектуре WorldWiki |
|---|---|---|
| **Файловая система (JSON / Markdown)** | Прямая читаемость файлов, отсутствие сторонних библиотек. | Отсутствие транзакционной ACID-модели; необходимость полной перезаписи файла при изменении атрибута; сложность поиска $O(N)$; отсутствие каскадной целостности; риск порчи при сбое питания. |
| **Встраиваемые реляционные СУБД (SQLite, DuckDB)** | Транзакционность ACID, хранение в одном файле, нулевая конфигурация (zero-config). | Жесткая реляционная схема; необходимость промежуточных таблиц связей (junction tables); отсутствие декларативного графового синтаксиса (требуются рекурсивные CTE); отсутствие нативных векторных индексов без сторонних C-расширений. |
| **Клиент-серверные СУБД (PostgreSQL)** | Высокая надежность, поддержка JSONB, расширения `pgvector` и `Apache AGE`. | Требует постоянного фонового сервиса, сетевых портов и прав администратора; потребление от 200–300 Мбайт ОЗУ; непригодность для поставки в виде портативного десктопного приложения. |
| **Графовые СУБД (Neo4j)** | Нативная графовая модель, язык запросов Cypher, эффективный обход связей. | Требует предустановленной Java-машины (JVM); потребление от 1.5–2.0 Гбайт ОЗУ в режиме простоя; архитектура выделенного сервера. |
| **Документные NoSQL СУБД (MongoDB)** | Гибкая бессхемная модель документов (BSON), полиморфизм карточек. | Отсутствие нативных графовых ребер связей (эмуляция через `$lookup`); необходимость системного демона `mongod`; отсутствие встраиваемой библиотеки. |
| **Встраиваемая мультимодельная СУБД SurrealDB (Выбор проекта)** | 1. Мультимодельность: объединяет Document, Graph (`TYPE RELATION`), Vector и Fulltext в едином движке.<br>2. Встраиваемость: компилируется непосредственно в процесс приложения через движок SurrealKV без внешних служб.<br>3. Язык SurrealQL: нативные графовые операторы, события (`EVENTS`) и функции (`FUNCTIONS`). | Необходимость реализации прикладных адаптеров доступа к данным. |

На основании анализа в качестве СУБД выбрана встраиваемая мультимодельная СУБД **SurrealDB** с движком **SurrealKV**, обеспечивающая сочетание транзакционной надежности, бессхемных динамических атрибутов и нативных графовых ребер без использования сетевых служб.

### 2.7.2. Обоснование выбора платформы десктопного приложения
Для реализации клиентского интерфейса рассматривались три технологические платформы:
1. **Electron:** высокая распространенность, однако значительное потребление оперативной памяти (от 300–500 Мбайт) из-за упаковки полного экземпляра браузера Chromium и среды Node.js в каждый дистрибутив.
2. **C# / WPF / .NET MAUI:** высокая производительность, однако жесткая привязка к экосистеме Microsoft Windows и сложность реализации гибких интерактивных веб-компонентов разметки.
3. **Tauri 2.x + Rust (Выбор проекта):** использование нативного системного движка WebView2 (встроенного в Windows 10/11) в сочетании с высокопроизводительным системным кодом на языке Rust. Обеспечивает минимальный размер исполняемого файла (менее 15 Мбайт), низкое потребление памяти (от 40–60 Мбайт ОЗУ) и максимальную скорость вычислений.

### 2.7.3. Обоснование выбора стека пользовательского интерфейса
1. **Vue 3 (Composition API) и TypeScript:** декларативная реактивная модель, строгая статическая типизация, высокая производительность благодаря виртуальному дереву DOM и компиляции шаблонов.
2. **Vite:** высокоскоростной инструмент сборки на основе нативных ES-модулей.
3. **Pinia:** легковесный типобезопасный менеджер глобального состояния.
4. **CSS Custom Properties (дизайн-токены):** отказ от тяжелых утилитарных фреймворков (TailwindCSS) в пользу чистой архитектуры модульных токенов, что обеспечивает полную изоляцию стилей и динамическое переключение тем.
