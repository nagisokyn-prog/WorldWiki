# ПРИЛОЖЕНИЕ Б. СРАВНИТЕЛЬНЫЙ АНАЛИЗ ТЕХНОЛОГИЧЕСКОГО СТЕКА И АРХИТЕКТУРНЫХ ПАТТЕРНОВ

В настоящем приложении приведены развёрнутые матрицы сопоставительного анализа альтернативных СУБД, движков текстового редактора и архитектурных паттернов бэкенда и фронтенда, обосновывающие выбор технологического стека АС «WorldWiki» (раздел 2.7).

---

## Б.1. Сравнительный анализ СУБД и хранилищ данных

Таблица Б.1 — Сравнительный анализ альтернативных СУБД и хранилищ данных

| Класс СУБД / Хранилища | Достоинства | Ограничения применительно к архитектуре WorldWiki |
|---|---|---|
| **Файловая система (JSON / Markdown)** | Прямая читаемость файлов, отсутствие сторонних библиотек. | Отсутствие транзакционной ACID-модели; необходимость полной перезаписи файла при изменении атрибута; сложность поиска $O(N)$; отсутствие каскадной целостности; риск порчи при сбое питания. |
| **Встраиваемые реляционные СУБД (SQLite, DuckDB)** | Транзакционность ACID, хранение в одном файле, нулевая конфигурация (zero-config). | Жесткая реляционная схема; необходимость промежуточных таблиц связей (junction tables); отсутствие декларативного графового синтаксиса (требуются рекурсивные CTE). |
| **Клиент-серверные СУБД (PostgreSQL)** | Высокая надежность, поддержка JSONB, расширения `pgvector` и `Apache AGE`. | Требует постоянного фонового сервиса, сетевых портов и прав администратора; потребление от 200–300 Мбайт ОЗУ; непригодность для поставки в виде портативного десктопного приложения. |
| **Графовые СУБД (Neo4j)** | Нативная графовая модель, язык запросов Cypher, эффективный обход связей. | Требует предустановленной Java-машины (JVM); потребление от 1.5–2.0 Гбайт ОЗУ в режиме простоя; архитектура выделенного сервера. |
| **Документные NoSQL СУБД (MongoDB)** | Гибкая бессхемная модель документов (BSON), полиморфизм карточек. | Отсутствие нативных графовых ребер связей (эмуляция через `$lookup`); необходимость системного демона `mongod`; отсутствие встраиваемой библиотеки. |
| **Встраиваемая мультимодельная СУБД SurrealDB (Выбор проекта)** | 1. Мультимодельность: объединяет Document, Graph (`TYPE RELATION`) и Fulltext в едином движке.<br>2. Встраиваемость: компилируется непосредственно в процесс приложения через движок SurrealKV без внешних служб.<br>3. Язык SurrealQL: нативные графовые операторы, события (`EVENTS`) и функции (`FUNCTIONS`). | Необходимость реализации прикладных адаптеров доступа к данным. |

## Б.2. Сравнительный анализ движков текстового редактора

Таблица Б.2 — Сравнительный анализ движков текстового редактора

| Движок | Достоинства | Ограничения применительно к WorldWiki |
|---|---|---|
| **Quill** | Простой API, формат операций `Delta`. | Плоская линейная модель документа неудобна для вложенных семантических блоков и интерактивных Vue-компонентов внутри текста. |
| **Editor.js** | Чисто блочный JSON-вывод, каждый абзац — отдельный виджет. | Разрывная блочная модель ломает сквозное выделение и копирование текста через несколько абзацев при потоковом письме длинных глав. |
| **Slate.js / Lexical** | Высокая гибкость AST и производительность. | Ориентированы в первую очередь на экосистему React; интеграция кастомных интерактивных узлов во Vue 3 требует сложных обёрток. |
| **Monaco / CodeMirror** | Отличная работа с кодом и чистым Markdown. | Отсутствует WYSIWYG-режим с произвольными инлайн-виджетами (интерактивные ссылки `((Сущность))`, маркеры абзацев). |
| **Tiptap v3 / ProseMirror (Выбор проекта)** | Типизированная схема документа (`Node`/`Mark`), транзакционный Undo/Redo, прямой экспорт JSON AST и нативный `VueNodeViewRenderer` для встраивания Vue-компонентов прямо в текст. | Более высокий порог входа при разработке кастомных расширений. |

## Б.3. Сравнительный анализ архитектурных паттернов бэкенда и фронтенда

Таблица Б.3 — Сравнительный анализ архитектурных стилей бэкенда

| Архитектурный стиль | Суть и достоинства | Ограничения и решение для WorldWiki |
|---|---|---|
| **Слоистая (Layered / N-tier)** | Классическое разделение `Presentation -> BLL -> DAL`, низкий порог входа. | Бизнес-логика (`BLL`) напрямую зависит от слоя БД (`SurrealDB`); невозможно тестировать сценарии без поднятия СУБД. **Отклонена.** |
| **Луковая (Onion Architecture)** | Инверсия зависимостей к центру (домен в центре, инфраструктура на внешнем кольце). | В рамках одного пакета границы между кольцами держатся только на соглашениях, без физического запрета импортов. |
| **Чистая (Clean Architecture)** | Четкое разделение `Entities`, `Use Cases`, `Interface Adapters`. | Задает общие принципы, но не фиксирует конкретный механизм портов/адаптеров и изоляцию на уровне компилятора. |
| **Vertical Slice Architecture** | Группировка кода вокруг независимых сценариев (фич) без общих слоев. | В WorldWiki доменные инварианты (шкала $t_{\text{abs}}$, граф сущностей, AST) сквозные; вертикальные срезы привели бы к дублированию доменной логики. **Отклонена.** |
| **CQRS** | Разделение моделей записи (Commands) и чтения (Queries). | Применяется **внутри ядра как дополнение** (мастер-документ `chapters.content` для записи и `text_blocks` / `SurrealQL`-функции аналитики для чтения). |
| **Гексагональная (Ports & Adapters, Выбор проекта)** | Изоляция чистого домена и сценариев через абстрактные трейты `ports`, физически закрепленная Cargo-крейтами (`core`, `domain`, `ports`, `application`, `infrastructure`, `tauri`). | Требует больше шаблонного кода маппинга DTO, но гарантирует 0 внешних SDK в домене, тестирование на `InMemory`-моках и контроль границ компилятором и статическим анализатором. |

Таблица Б.4 — Сравнительный анализ структурных подходов фронтенда

| Подход | Достоинства | Ограничения и решение для WorldWiki |
|---|---|---|
| **Atomic Design** | Удобная иерархия переиспользуемых визуальных элементов (атомы, молекулы, организмы). | Делит код по визуальному размеру, а не по бизнес-логике; применён **только для базового UI-Kit (`@worldwiki/components`)**. |
| **Domain-Driven Design (DDD)** | Глубокое моделирование агрегатов, инвариантов и Bounded Contexts. | Полноценный DDD реализуется на бэкенде (Rust); на клиенте дублирование агрегатов избыточно. |
| **Clean / Hexagonal (на фронте)** | Максимальная изоляция UI от транспорта. | Избыточна для клиентского слоя поверх реактивного Vue 3; достаточно тонкого API-клиента (`api.client.ts`). |
| **Feature-Sliced Design (FSD, Выбор проекта)** | Строгая иерархия слоев (`app` $\to$ `features` $\to$ `composables` $\to$ `stores`/`services` $\to$ `types`/`utils`), изоляция доменных фич и однонаправленные зависимости. | Требует дисциплины при размещении новых модулей, но полностью исключает перекрёстные «спагетти-импорты». |

Таблица Б.5 — Сравнительный анализ паттернов потока данных фронтенда

| Паттерн | Суть | Применимость и решение для WorldWiki |
|---|---|---|
| **MVC / MVP** | Разделение на Model, View и императивный Controller/Presenter. | Устарел для реактивных компонентных фреймворков: презентеры дублируют управление DOM. **Отклонен.** |
| **Islands Architecture** | Статичный HTML с изолированными интерактивными JS-островками. | Предназначен для SSR и контентных веб-сайтов; неприменим к насыщенному интерактивному десктопному SPA. **Отклонен.** |
| **Flux / Redux (в чистом виде)** | Строгий круговой поток `View -> Action -> Dispatcher/Reducer -> Store -> View`. | Избыточный boilerplate редьюсеров для локальных форм; **принцип однонаправленного потока данных** используется через `Pinia` для глобального состояния (`.vue -> use*.ts -> Store/Service -> api.client.ts -> Tauri IPC`). |
| **MVVM (Выбор проекта)** | Реактивное связывание `View` и `ViewModel` над `Model`. | Реализован через 4-компонентную схему: `*.vue` (`View`, 0 бизнес-логики), `use*.ts` (`ViewModel`), `*.model.ts` и `stores/` (`Model`), что позволяет тестировать всю логику в Vitest без монтирования DOM. |
