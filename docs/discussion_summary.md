## 1. Ответы на замечания преподавателя

### 1.1 «Кольцевая связь Проекты → Типы_сущностей → Сущности_лора»

Это не порочный цикл, а **контекстно-ограниченная алмазная зависимость**.

**Типы сущностей — проектные, но долгоживущие:**
- У каждого проекта своя версия типа «Персонаж» с уникальными полями
- Фэнтези: `fields_schema: ["Количество маны", "Класс магии", "Фракция"]`
- Киберпанк: `fields_schema: ["Количество имплантов", "Хакерский уровень", "Нейросеть"]`
- `entity_schemas.project_id` фиксирует «кто создал», а не жёсткое владение
- **Важно**: при удалении проекта `entity_schemas` **не удаляются** — каскад их не трогает. Автор сохраняет настроенные шаблоны для новых проектов. Это осознанное решение.

**Инвариант классификации**: «ТИПИЗИРУЮТ» работает только внутри проекта — `entity_schema.project_id = entity.project_id`. Тип из Проекта А не типизирует сущности Проекта Б.

**Что написать в тексте 2.8.5.2**: *«Отношение „ТИПИЗИРУЮТ" является контекстно-ограниченным: схема типа применяется исключительно к сущностям того же проекта, что обеспечивает изоляцию онтологий вымышленных миров. Жизненный цикл `ТИПОВ_СУЩНОСТЕЙ` не зависит от проекта-создателя — шаблоны сохраняются после удаления проекта для повторного использования в новых произведениях.»*

### 1.2 «Арки — разобраться, нумерация на разных уровнях»

**Философия изменилась**: иерархия дерева рукописи была `Том → Арка → Глава`, стала `Том → Глава`. Арки **не исчезают из предметной области** — они переосмысляются.

**Новая концепция арок**:
- Арка = именованная сюжетная линия (сторилайн)
- Три вида: арка персонажа, арка события, арка отношений
- **M:N с главами**: одна глава принадлежит многим аркам, одна арка охватывает главы из нескольких томов (пример: Кагуя-сама — арки тянутся через весь сериал)
- **0..N к сущностям лора**: арка привязана к конкретному персонажу / паре персонажей / фракции

**В UX** (по твоим заметкам):
- В карточке главы: поле арок как теги (`tags-field-vue` аналог) — компактно, много значений
- В аккордеоне планирования (`parent-plan-accordion`): каждая арка = отдельная вкладка со своим планом
- Блок `dropdown-container` (текущий) — срезать в 3-4 раза по длине

**Нумерация**: атрибут `Порядковый_номер` у `ГЛАВ_РУКОПИСИ` — порядок **внутри тома**, не глобальный. Это надо явно указать в тексте.

### 1.3 «Динамические поля и типы связей — атрибуты или сущности?»

| Концепт | Квалификация | Обоснование |
|---|---|---|
| `Спецификация_полей` (`fields_schema`) | ✅ **Атрибут** `ТИПОВ_СУЩНОСТЕЙ` | JSON-шаблон структуры, не самостоятельный объект |
| `Динамические_поля` (`entities.attributes`) | ✅ **Составной многозначный атрибут** `СУЩНОСТЕЙ_ЛОРА` | Конкретные значения полей экземпляра |
| `Типы_связей` (`relation_schemas`) | ❌ **Пропущена сущность** | В коде — самостоятельная таблица с `rel_key`, `rel_name`, `icon`, `directed`, `from_types/to_types`. Нужно добавить в ER как `ТИПЫ_СВЯЗЕЙ` |

### 1.4 «Ненаправленные связи — новое слово в ER»

В нотации Чена все связи семантически ненаправлены. Направленность — деталь реализации.

**Исправить в тексте**: заменить «ненаправленным или направленным» на **«рекурсивной (унарной) связью»** — стандартный термин ER-теории, легко объяснить:

> «Рекурсивная связь — это когда отношение замкнуто на одно и то же множество сущностей. Классический пример из учебника: сотрудник „РУКОВОДИТ" сотрудником. В WorldWiki: сущность лора „СВЯЗАНА_С" другой сущностью лора — персонаж может быть другом, врагом или родственником другого персонажа из того же множества.»

Про направленность: вынести отдельно — в реализации каждое ребро может быть направленным (`directed = true` в `ТИПАХ_СВЯЗЕЙ`). При асимметрии восприятия (Рудеус→Эрис ≠ Эрис→Рудеус) хранятся два отдельных направленных ребра.

### 1.5 «Фрагменты текста не связаны с героями — баг или фича?»

**Ответ**: недостаток изобразительных средств схемы — `((Имя))` в тексте сейчас делает только UI popup, в БД ничего не пишется.

**Решение: два уровня связи одновременно**

**Уровень 1 — авто (всегда)**: при сохранении главы парсить AST Tiptap → все `((Имя))` → `UPSERT appears_in(source='mention')`. Никаких новых таблиц.

**Уровень 2 — ручной (детальный)**: автор выделяет абзац → создаёт `plot_promise(kind='scene')` с `block_id` → указывает участников и локацию:

```
plot_promise(kind='scene', block_id='para-042'):
  participant_ids: [entity:rudeus, entity:eris]
  location_id:    entity:forest
  timeline_event_id: event:confrontation
```

**Изменения в БД (4 поля, нет новых таблиц)**:
```sql
DEFINE FIELD OVERWRITE source ON appears_in
    TYPE string DEFAULT 'mention'; -- 'mention' | 'manual' | 'scene'

DEFINE FIELD OVERWRITE participant_ids ON plot_promises
    TYPE option<array<record<entities>>>;
DEFINE FIELD OVERWRITE location_id ON plot_promises
    TYPE option<record<entities>>;
DEFINE FIELD OVERWRITE timeline_event_id ON plot_promises
    TYPE option<record<timeline_events>>;
```

**Реальный недостаток**: `timeline_events.chapter_id` = FK на одну главу. Для нелинейных произведений (Kill Bill) одно событие раскрывается в нескольких главах → нужна **M:N связь событий с главами**.

### 1.6 «Схема громоздкая — разбить на три проекции»

Решение: **три отдельные диаграммы** вместо одной монолитной.

| Диаграмма | Название | Содержимое |
|---|---|---|
| **2.1** | Ядро предметной области | `ПРОЕКТЫ`, `ТОМА`, `ГЛАВЫ`, `ТИПЫ_СУЩНОСТЕЙ`, `ТИПЫ_СВЯЗЕЙ`, `СУЩНОСТИ_ЛОРА`, `СОБЫТИЯ_КАЛЕНДАРЯ`, `СЮЖЕТНЫЕ_АРКИ`, `СЮЖЕТНЫЕ_ОБЕЩАНИЯ`, `ПЛАНЫ` |
| **2.2** | ИИ-пространство (изолированно) | `СЕССИИ_ИИ`, `СООБЩЕНИЯ_ИИ`, `НАВЫКИ_ИИ`, `ВЕБ_ИСТОЧНИКИ`, `ФАКТЫ_ИССЛЕДОВАНИЙ` — только внутренние связи |
| **2.3** | Мост: ИИ ↔ Ядро | Только пограничные сущности обеих схем + межслойные связи |

**Схема 2.3 — мост (самая архитектурно значимая):**
```
[Ядро]                              [ИИ-слой]

ПРОЕКТЫ ──(ВЕДУТ 1:N)────────────── СЕССИИ_ИИ
                                         │
ГЛАВЫ_РУКОПИСИ ─(ФОКУСИРУЮТ 0..1)── СЕССИИ_ИИ
                                         │
                                  СООБЩЕНИЯ_ИИ
                                         │ (ОБОСНОВЫВАЮТ M:N)
                                  ФАКТЫ_ИССЛЕДОВАНИЙ ←── ВЕБ_ИСТОЧНИКИ
```

Эта схема показывает что ИИ-слой — **аддитивный**: подключается к ядру только через `ПРОЕКТЫ` и `ГЛАВЫ_РУКОПИСИ`, не затрагивая остальные сущности.

### 2.1 Унификация «Нарративных блоков»

`plot_promises` становится **универсальным нарративным контейнером** с расширенным `kind`:

```
kind:
  'gun'           → Чеховское ружьё (уже есть)
  'foreshadowing' → Предзнаменование (уже есть)
  'mystery'       → Тайна (уже есть)
  'question'      → Вопрос (уже есть)
  ─────────────────────────────────────────────
  'scene'         → НОВЫЙ: Сцена/Эпизод (block_id = НЕ NULL)
  'conflict'      → НОВЫЙ: Конфликт (стороны + фазы в progressions)
```

**Правило различения**: `block_id ≠ NULL` → сцена (привязана к абзацу); `block_id = NULL` → глава-уровень (ружьё, таймлайн).

`timeline_events` остаётся **чистой системой diegetic-координат** (M_abs, факты мира). Связь через `plot_promise.timeline_event_id`.

### 2.2 Унификация правой панели редактора

Три аккордеона (Таймлайн + Участники + Обещания) → один `PromisesPanel` как центральный хаб:

| Что | Сейчас | Предложение |
|---|---|---|
| `TimelinePanel` | отдельный аккордеон | → секция `kind='timeline_event'` в `PromisesPanel` |
| `ParticipantsPanel` | отдельный аккордеон | → поле `participant_ids` на каждой сцене |
| `PromisesPanel` | отдельный компонент | становится **центральным хабом** |
| `semanticTag` (desc/dialog) | только в AST | синхронизируется с прикреплённой сценой |

**Внимание**: `chapters.participants = array<string>` и `chapters.timeline_events` (FLEXIBLE) — нужна миграция данных.

## 3. Новые фичи: Хронологическое окно и Граф связей

> **Важно**: реализация без ИИ-слоя — чистый алгоритм (SurrealDB запросы + фронтенд рендеринг)

### 3.1 Проблема нелинейного повествования

Произведения типа «Убить Билла» или «Ночь перед» создают **дуализм нарративного времени**:

```
Diegetic time (время мира):   M_abs — когда событие ПРОИЗОШЛО
Narrative time (время чтения): Гл.N — когда читатель УЗНАЁТ о событии
```

Пример из Mushoku Tensei (Рудеус/Эрис):
- В `M_abs = T` (одно время мира): Рудеус злится, Эрис любит
- Злость Рудеуса раскрыта в Гл.15 Тома 7
- Любовь Эрис раскрыта в Гл.3 Тома 11
- Автор пишет линейно и **теряет нить** — именно эту проблему решают новые инструменты

---

### 3.2 Фича А: Хронологическое окно (Timeline Inspector)

**Концепция**: двойная ось на одном экране.

```
НАРРАТИВНАЯ ОСЬ (порядок чтения):
  [Гл.1]──[Гл.2]──[Гл.5]──────────[Гл.11]──[Гл.15]
     │              │                  │        │
     │              │                  │        │
  ───┼──────────────┼──────────────────┼────────┼──────►
  [Соб_Б]       [Соб_А]           [Соб_В]  [Соб_Г]
  M_abs:340     M_abs:100         M_abs:380  M_abs:410

DIEGETIC ОСЬ (реальное время мира, M_abs)
```

Вертикальные линии = «в какой главе раскрывается какое событие». Перевёрнутые/пересекающиеся линии = нелинейность. Автор сразу видит запутанную хронологию.

**Фильтры**:
- По персонажу (swimlane для каждой сущности)
- По арке
- По тому/главе

**Режимы**:
- **Режим автора**: видит все события и все раскрытия (полная картина)
- **Режим читателя**: скрывает события, ещё не раскрытые до выбранной главы

**Данные в БД (уже есть)**:
- `timeline_events.m_abs` — diegetic-координата
- `timeline_events.chapter_id` → нужно расширить до M:N (одно событие, несколько глав)
- `participates_in (entities → events)` — кто участвует
- `contains (volumes → chapters)` — иерархия

---

### 3.3 Фича Б: Граф связей с временным срезом («Паутина»)

**Концепция**: Force-Directed Graph (паутина), которая **перестраивается** при выборе главы или M_abs-даты.

**Алгоритм** (без ИИ):
```
1. Пользователь выбирает: [Глава N] или [M_abs = T]
2. SurrealDB запрос:
     SELECT * FROM entity_rel
     WHERE start_chapter.sort_order ≤ N ≤ end_chapter.sort_order
       AND project_id = $proj
3. Rust WASM Worker вычисляет позиции узлов (force layout)
4. Canvas 2D рисует паутину (60fps)
```

**✅ Решение по рендерингу (зафиксировано)**: Rust → WASM (Worker) для физики + Canvas 2D для рендеринга.
- wgpu отклонён: избыточен для 2D-графа, проектировался под 3D
- D3.js отклонён: однопоточный, ограниченный
- Rust-код компилируется через `wasm-pack`, физика (force simulation) выполняется в WebWorker → не блокирует UI
- Canvas 2D достаточен для рисования паутины из 50–500 узлов
- Опционально на будущее: WebGL через `regl`/`pixi.js` для 1000+ узлов

**Визуальная кодировка рёбер**:
- Толщина = `|strength|`
- Цвет = знак `strength` (🟢 положительное / 🔴 отрицательное)
- Стрелка = `directed = true` в `relation_schemas`
- Пунктир = ребро «известно автору, но ещё не раскрыто читателю»

**✅ Решение по визуализации двух направлений (зафиксировано)**:

Между двумя узлами рисуются **две параллельные кривые Безье** со стрелками:
```
         ╭── strength: -80 (красная, толще) ──╮
[Рудеус]                                       [Эрис]
         ╰── strength: +95 (зелёная) ──────────╯

Кодировка каждой линии:
  - Цвет:    hsl(0°..120°) по значению strength (-100 → +100)
  - Толщина: |strength| / 20  →  диапазон 0..5px
  - Смещение от центра: ±6px (чтобы не перекрывались)
  - Стрелка на конце (directed = true)
  - Пунктир: ребро активно в мире, но ещё не раскрыто в выбранной главе
```

**Следствие для БД**: `entity_rel` должен хранить два отдельных записи для `A→B` и `B→A`. Это уже поддерживается (`TYPE RELATION IN entities OUT entities`). UI при создании должен предлагать «Добавить обратную связь?».

**Связь с существующим кодом**: [`RelationshipBlock.vue`](file:///c:/Users/Kuzma/Desktop/WorldWiki/apps/spa/src/ts/shared/ui/RelationshipBlock/RelationshipBlock.vue) уже реализует двустороннее редактирование (Сторона А / Сторона Б) с динамическими контейнерами и `ManuscriptPointPicker`. Это задел для формы создания/редактирования рёбер в графе.

**Два режима одного графа**:
- **«Глазами читателя»** (narrative): рёбра появляются в порядке раскрытия в главах
- **«Глазами автора»** (diegetic): видны все рёбра, активные в выбранный M_abs

### 3.4 Открытый вопрос: M_abs у рёбер `entity_rel`

Сейчас временные границы ребра — это главы (`start_chapter`, `end_chapter`).  
Для слайдера по M_abs нужно ли хранить явно `start_m_abs` / `end_m_abs`?

**✅ Решение: Комбо-подход (зафиксировано)**

```
Для каждого ребра entity_rel:

1. Есть start_chapter?
   └► Есть у этой главы timeline_events?
       ├► ДА → берём m_abs автоматически ✅
       └► НЕТ → красный ⚠ на ребре в графе паутины
               «Укажите дату начала для этой связи»
               [ссылка: Добавить событие к главе]

2. Автор вручную указывает → ⚠ снимается
```

Это **прогрессивное заполнение**: граф работает с тем что есть, мягко подсказывает где данных не хватает, не блокирует работу.

### 5.2 Фича 2: Матрица участий (Cross-Reference Matrix)

**Самая быстрая в реализации, сразу даёт максимальный эффект.**

```
              Гл.1  Гл.2  Гл.3  Гл.4  Гл.5  Гл.6  ...
Рудеус         🔵    🔵    ——    🔵    🔵    🔵
Эрис           ——    🔵    🔵    ——    ——    ——    ← пропала на 4 главы
Паулс          🔵    ——    ——    ——    🔵    ——
Сильфиетт      ——    ——    🔵    🔵    🔵    🔵

⚠️ «Буровский» эффект: Паулс пропал с Гл.2 по Гл.4 — 3 главы без упоминания
```

**Данные**: `appears_in (entities → chapters)` — уже в БД, SELECT без JOIN.  
**Запрос**:
```sql
SELECT ->appears_in->chapters AS chapters FROM entities
WHERE project_id = $proj
GROUP BY id
```
**UI**: таблица `entities × chapters` с цветовыми ячейками. Фильтр по типу сущности, тому, арке.  
**Режимы ячейки**: `●` появляется, `○` упомянута (через `((Имя))`), `—` отсутствует, `💀` мертва.

### 5.3 Фича 3: Consistency Checker (Детектор противоречий)

**Полностью алгоритмический, никакого ИИ.**

```
⚠️ ОБНАРУЖЕНО 3 ПРОТИВОРЕЧИЯ:

🔴 [КРИТИЧНО] Персонаж «Гислэйн» умер в Гл.7 (M_abs=3400),
   но упоминается в Гл.12 (M_abs=5100) как живой
   → appears_in(char:gislein, ch:12) ⊕ entity.death_m_abs=3400

🟡 [ВНИМАНИЕ] Событие «Битва за Форклесс» (M_abs=450)
   раскрыто впервые в Гл.3, но в Гл.1 уже упоминается его исход
   → timeline_events.m_abs=450 < plot_promise.chapter_id(Гл.3)
   но appears_in содержит ссылку из Гл.1

🟡 [ВНИМАНИЕ] Локация «Северный Замок» разрушена в Гл.5,
   но персонаж «Рудеус» приходит туда в Гл.9
   → entity_rel(char:rudeus → loc:castle).end_chapter=Гл.5
   ⊕ appears_in(loc:castle, ch:9)
```

**Алгоритмы проверок**:
1. `Мёртвый персонаж жив` → `entity.death_m_abs < appears_in.chapter.m_abs`
2. `Раскрытие до события` → `plot_promise.progressions[planted].chapter.sort_order < timeline_event.chapter.sort_order`
3. `Разрушенная локация доступна` → `entity_rel.end_chapter < appears_in.chapter` (для локаций)
4. `Персонаж в двух местах одновременно` → два `appears_in` с одинаковым `m_abs` и разными локациями

### 5.4 Фича 4: Путь персонажа (Character Journey)

Вертикальная лента для одной выбранной сущности:

```
🧑 РУДЕУС — Путь через рукопись

Timeline:
  M_abs=0    Рождение (entity.birth_m_abs)
     │
  Гл.1 ─── [appears_in] ─── Встреча с Эрис
     │       ↕ entity_rel    strength: +30
  Гл.5 ─── [appears_in] ─── Импотенция (plot_promise: planted 🔫)
     │       ↕ entity_rel    strength: -80 (к Эрис)
  Гл.7 ─── [timeline_event] ─ Конфронтация
     │
  ─ ─ ─ ─ ─ ─ 4 главы без упоминания ─ ─ ─ ─ ─ ─
     │
  Гл.11 ── [appears_in] ─── Воссоединение
            [plot_promise: resolved ✅]
```

**Данные**: join по `appears_in` + `entity_rel` + `timeline_events` + `plot_promises` — всё есть.  
**UI**: вертикальный timeline-компонент, аналог ленты событий LinkedIn/GitHub.
