Это пример того как надо описывать ТЗ. Сначала даю тебе гост, а после уже ПРИМЕРНОЕ содержание того что ты должен сделать. Помни в ТЗ могут быть неточности, поправки, недочеты и прочее. Так же помни что в ТЗ могут быть ссылки на другие файлы. Тебе нужно будет их прочесть. Обращай внимание на ошибки в ТЗ и исправляй их. Со временем ты научишься сам писать ТЗ. Если ты чего-то не понимаешь или не знаешь как сделать, то не берись за работу. Почитай документацию, поищи в интернете, спроси меня.

# 📋 Памятка по написанию ТЗ на курсач

> Собрано из ГОСТ 34.602-89, статьи на Хабре и статьи Gaperton. Всё в одном месте — не надо скакать туда-сюда.

---

## 1. Что такое ТЗ по ГОСТ 34.602-89

ГОСТ 34.602-89 — это стандарт на **Техническое задание на создание автоматизированной системы (АС)**. Он распространяется на АС для автоматизации различных видов деятельности (управление, проектирование, исследование и т.д.) и устанавливает состав, содержание и правила оформления ТЗ.

**Ключевая мысль из Gaperton:** ТЗ по ГОСТ — это **не** Requirements Specification. Это **задание** (Task), а не просто перечень требований. ТЗ = ключевые требования + поэтапный план работ. Это единица планирования, ближайший аналог — Project Charter.

---

## 2. Структура ТЗ по ГОСТ 34.602-89

ТЗ содержит **9 основных разделов**. В зависимости от специфики проекта допускается: вводить дополнительные, исключать или объединять подразделы, оформлять разделы как приложения.

| №   | Раздел                                                                                                 |
| --- | ------------------------------------------------------------------------------------------------------ |
| 1   | Общие сведения                                                                                         |
| 2   | Назначение и цели создания (развития) системы                                                          |
| 3   | Характеристика объектов автоматизации                                                                  |
| 4   | Требования к системе                                                                                   |
| 5   | Состав и содержание работ по созданию системы                                                          |
| 6   | Порядок контроля и приемки системы                                                                     |
| 7   | Требования к составу и содержанию работ по подготовке объекта автоматизации к вводу системы в действие |
| 8   | Требования к документированию                                                                          |
| 9   | Источники разработки                                                                                   |

Также могут включаться **приложения** (расчёт ожидаемой эффективности, оценка научно-технического уровня).

---

## 3. Детальное содержание каждого раздела

### Раздел 1. Общие сведения

Что указываем:

1. **Полное наименование системы** и её условное обозначение
2. **Шифр темы** или шифр (номер) договора
3. **Наименование предприятий** разработчика и заказчика + реквизиты
4. **Перечень документов**, на основании которых создаётся система (кто и когда утвердил)
5. **Плановые сроки** начала и окончания работ
6. **Источники и порядок финансирования**
7. **Порядок оформления и предъявления** заказчику результатов работ

---

### Раздел 2. Назначение и цели создания (развития) системы

Состоит из двух подразделов:

#### 2.1. Назначение системы

- Вид автоматизируемой деятельности (управление, проектирование и т.п.)
- Перечень объектов автоматизации, на которых предполагается использовать систему
- Для АСУ: перечень автоматизируемых органов управления и управляемых объектов

#### 2.2. Цели создания системы

- Наименования и требуемые значения технических, технологических, производственно-экономических показателей объекта автоматизации, которые должны быть достигнуты
- **Критерии оценки достижения целей**

> 💡 **Мысль от Gaperton:** Это — **самая важная секция ТЗ**. Умение отделять **цели** от **задач** — ключевое.
>
> - **Задача** = что конкретно надо сделать (например, «разработать аудиокодек»)
> - **Цель** = зачем, ради решения какой проблемы (например, «для использования в конечном продукте» vs «для испытаний архитектурного прототипа»)
> - Если цель дублирует задачу — возможно, работа вообще не нужна.

---

### Раздел 3. Характеристика объектов автоматизации

- Краткие сведения об объекте автоматизации или ссылки на документы с такой информацией
- Сведения об **условиях эксплуатации** и характеристиках окружающей среды
- Для САПР: основные параметры и характеристики объектов проектирования

---

### Раздел 4. Требования к системе

Состоит из трёх подразделов:

- Требования к системе **в целом**
- Требования к **функциям (задачам)**, выполняемым системой
- Требования к **видам обеспечения**

#### 4.1. Требования к системе в целом

| Пункт                                        | Что описываем                                                                                                                                                   |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Структура и функционирование                 | Перечень подсистем, их назначение, иерархия, централизация, способы связи, режимы функционирования, диагностирование, перспективы развития                      |
| Численность и квалификация персонала         | Требования к числу пользователей, их подготовка, режим работы                                                                                                   |
| Показатели назначения                        | Параметры, характеризующие степень соответствия системы её назначению (для АСУ: приспособляемость, пределы модернизации, вероятностно-временные характеристики) |
| Надёжность                                   | Вероятность безотказной работы, наработка на отказ и т.п.                                                                                                       |
| Безопасность                                 | Защита от электрического тока, электромагнитных полей, шумов, уровни освещённости, вибрация                                                                     |
| Эргономика и техническая эстетика            | Качество взаимодействия человек-машина, комфортность работы                                                                                                     |
| Транспортабельность                          | Для подвижных АС: конструктивные требования, транспортные средства                                                                                              |
| Эксплуатация, обслуживание, ремонт, хранение | Условия эксплуатации, регламент, площади, энергоснабжение, запасные изделия                                                                                     |
| Защита информации от НСД                     | Требования по НТД отрасли заказчика                                                                                                                             |
| Сохранность информации при авариях           | Перечень событий (аварии, отказы, потеря питания), при которых данные должны сохраниться                                                                        |
| Защита от внешних воздействий                | Радиоэлектронная защита, стойкость к внешним воздействиям                                                                                                       |
| Патентная чистота                            | Перечень стран, в отношении которых обеспечивается патентная чистота                                                                                            |
| Стандартизация и унификация                  | Степень использования стандартных методов, типовых решений, классификаторов                                                                                     |
| Дополнительные требования                    | Тренажёры, сервисная аппаратура, особые условия эксплуатации                                                                                                    |

#### 4.2. Требования к функциям (задачам), выполняемым системой

- По каждой подсистеме: перечень функций/задач, подлежащих автоматизации
- При создании в очереди: перечень функций, вводимых в 1-й и последующих очередях
- **Временной регламент** реализации каждой функции
- Требования к **качеству реализации**: форма выходной информации, точность, время выполнения, одновременность, достоверность
- Перечень и **критерии отказов** для каждой функции (если задаются требования по надёжности)

#### 4.3. Требования к видам обеспечения

| Вид обеспечения             | Что описываем                                                                                                                                                                                                                                                       |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Математическое**          | Состав, область применения, способы использования математических методов, моделей, алгоритмов                                                                                                                                                                       |
| **Информационное**          | Состав, структура, способы организации данных; информационный обмен; совместимость со смежными системами; классификаторы; СУБД; сбор, обработка, передача; защита данных; контроль, хранение, обновление, восстановление; юридическая сила документов (ГОСТ 6.10.4) |
| **Лингвистическое**         | Языки программирования, языки взаимодействия пользователей и ТС, кодирование/декодирование, языки ввода-вывода, манипулирования данными, описания предметной области, способы организации диалога                                                                   |
| **Программное**             | Перечень покупных ПС; независимость от СВТ и ОС; качество ПО; согласование с фондом алгоритмов и программ                                                                                                                                                           |
| **Техническое**             | Виды ТС, комплексов ТС, программно-технических комплексов; функциональные, конструктивные и эксплуатационные характеристики                                                                                                                                         |
| **Метрологическое**         | Перечень измерительных каналов; точность измерений; метрологическая совместимость; управляющие и вычислительные каналы; метрологическая аттестация (государственная/ведомственная)                                                                                  |
| **Организационное**         | Структура и функции подразделений; порядок взаимодействия персонала АС и объекта автоматизации; защита от ошибочных действий персонала                                                                                                                              |
| **Методическое** (для САПР) | Перечень НТД, стандартов, нормативов, методик                                                                                                                                                                                                                       |

### Раздел 5. Состав и содержание работ по созданию (развитию) системы

- Перечень **стадий и этапов** работ (в соответствии с ГОСТ 24.601)
- **Сроки выполнения** каждого этапа
- Перечень **организаций-исполнителей**
- Ссылки на документы, подтверждающие согласие организаций на участие
- Перечень документов, предъявляемых по окончании стадий/этапов (по ГОСТ 34.201-89)
- Вид и порядок проведения **экспертизы** технической документации
- Программа работ по обеспечению надёжности (при необходимости)
- Перечень работ по **метрологическому обеспечению** со сроками и исполнителями

> 💡 **Мысль от Gaperton:** В ГОСТ есть рекомендательный список стадий и этапов, но на практике — **полная свобода** в определении количества этапов, их названий и состава работ. Этап имеет: срок окончания, название, описание результатов, перечень видов работ. Этап проверяется **по результатам**, а не по активностям.

---

### Раздел 6. Порядок контроля и приемки системы

- **Виды, состав, объём и методы испытаний** системы и её частей
- **Общие требования к приёмке** работ по стадиям: перечень участвующих организаций, место и сроки проведения
- Порядок согласования и утверждения приёмочной документации
- **Статус приёмочной комиссии** (государственная, межведомственная, ведомственная)

> 💡 **Мысль от Gaperton:** Если вас волнует отсутствие детально расписанных требований в ТЗ — не волнуйтесь. Есть документ **«Программа и методика испытаний»** — это тест-план, который фиксирует требования в конструктивной форме. Включайте первую версию этого документа в результат первого этапа.

---

### Раздел 7. Требования к составу и содержанию работ по подготовке объекта автоматизации к вводу системы в действие

Перечень основных мероприятий и их исполнителей:

- Приведение поступающей информации к виду, пригодному для обработки
- Изменения, необходимые в объекте автоматизации
- Создание условий функционирования, гарантирующих соответствие системы требованиям ТЗ
- Создание необходимых подразделений и служб
- Сроки и порядок комплектования штатов и обучения персонала

Для АСУ дополнительно:

- Изменения применяемых методов управления
- Создание условий для работы компонентов АСУ

---

### Раздел 8. Требования к документированию

- Согласованный перечень подлежащих разработке **комплектов и видов документов** (по ГОСТ 34.201-89 и НТД отрасли)
- Перечень документов, выпускаемых на **машинных носителях**
- Требования к **микрофильмированию** документации
- Требования по документированию комплектующих элементов межотраслевого применения (по ЕСКД и ЕСПД)
- При отсутствии ГОСТов — дополнительные требования к составу и содержанию документов

---

### Раздел 9. Источники разработки

Перечень документов и информационных материалов, на основании которых разрабатывалось ТЗ:

- Технико-экономическое обоснование
- Отчёты о законченных НИР
- Информационные материалы на отечественные и зарубежные системы-аналоги
- И другие

## 4. Правила оформления (кратко)

- Если какое-либо требование не может быть конкретизировано на момент составления ТЗ, указывают: _«Окончательное требование (значение) уточняется в процессе ... и согласовывается протоколом с ... на стадии ...»_ — при этом в текст ТЗ изменений не вносят
- На титульном листе — подписи заказчика, разработчика и согласующих организаций с гербовыми печатями
- Подписи разработчиков ТЗ и должностных лиц, участвующих в согласовании — на **последнем листе**
- Допускается размещать на титульном листе: гриф секретности, код работы, регистрационный номер ТЗ

---

## 5. Порядок разработки, согласования и утверждения ТЗ

- Согласование проекта ТЗ можно оформить отдельным документом (письмом) — тогда под грифом «Согласовано» делают ссылку на него
- Утверждение — руководители предприятий разработчика и заказчика
- Перед утверждением ТЗ проверяется службой **нормоконтроля** разработчика и при необходимости — **метрологической экспертизой**
- Копии утверждённого ТЗ в **10-дневный срок** направляются участникам создания системы
- **Изменения к ТЗ не допускается утверждать** после представления системы (или её очереди) на приёмо-сдаточные испытания

## 6. Сравнение с другими стандартами (из Хабра)

| Стандарт                    | Для чего                                        | Структура                                                                                                                            |
| --------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **ГОСТ 34.602-89**          | Системы в целом (ПО + железо + люди + процессы) | 9 разделов, описаны выше                                                                                                             |
| **ГОСТ 19.201-78** (ЕСПД)   | Только программное обеспечение                  | Введение, основания, назначение, требования к ПО, документация, ТЭП, стадии, приёмка, приложения                                     |
| **IEEE 830-1998**           | SRS (Software Requirements Specification)       | Введение, общее описание, детальные требования (интерфейсы, функционал, производительность, нефункциональные требования), приложения |
| **ISO/IEC/IEEE 29148-2011** | Замена 830, 1233, 1362                          | SyRS (системные требования) + SRS (требования к ПО)                                                                                  |
| **RUP**                     | Итеративная разработка                          | Традиционный шаблон (как IEEE 830) или упрощённый через use cases                                                                    |

> **Вывод из Хабра:** При правильном использовании любого стандарта можно получить хорошее ТЗ. Главное — **чтобы ТЗ не превратилось в ХЗ**. Содержание важнее формы.

## 7. Философия ГОСТ-овского стиля управления (Gaperton)

### 7.1. ТЗ — это задание, а не спецификация требований

- Правильное ТЗ **короче**, чем SRS
- Секция «технические требования» содержит только **ключевые требования**, определяющие успех проекта
- Вторая главная секция — **поэтапный план работ** (таблица: этап, срок, результаты, виды работ, сумма при сдельной оплате)

### 7.2. Этап проверяется по результатам, а не по активностям

- ГОСТ не содержит инструментов контроля, выполняются ли заявленные активности
- Этап проверяется **по результатам**. Точка.
- Активности указываются, чтобы заказчику было понятно, чем люди занимаются и почему такие сроки/суммы

### 7.3. Иерархия ТЗ

- Вместо WBS и задач в таск-трекере — **иерархия ТЗ**
- Крупное ТЗ дробится на более мелкие ТЗ для более мелких работ
- Две главные секции на любом уровне: **технические требования + поэтапный план**

### 7.4. Чем ГОСТ отличается от классики

| ГОСТ                                                         | Классика (PMBOK и т.п.)              |
| ------------------------------------------------------------ | ------------------------------------ |
| Объединяет планирование и управление требованиями            | Разделяет план и требования          |
| Фокус на **результатах** работ                               | Фокус на **процессах** и активностях |
| Одна и та же техника для программы и проекта                 | Разные подходы                       |
| Нет отдельной роли «менеджера» — все инженеры                | Выделенный менеджер                  |
| Совместим со стилем **Auftragstaktik** (управление по целям) | Часто управление по задачам          |

### 7.5. Как это выглядит в таск-трекере (например, Redmine)

- Иерархия ТЗ = иерархия проектов и подпроектов
- Этапы = версии для каждого проекта
- Технические требования = wiki или тикеты

## 8. Чек-лист перед сдачей ТЗ

- [ ] Все 9 разделов присутствуют (или обосновано исключены/объединены)
- [ ] Цели отделены от задач
- [ ] Каждая цель имеет **критерии оценки достижения**
- [ ] Функции описаны с временным регламентом и критериями качества
- [ ] Этапы работ имеют **конкретные сроки и результаты**
- [ ] Порядок приёмки описан (виды испытаний, комиссия, документация)
- [ ] Источники разработки перечислены
- [ ] ТЗ прошло нормоконтроль
- [ ] Подписи и печати на титульном листе
- [ ] Нет противоречий между разделами

## Раздел 2. Назначение и цели

### 2.1. Назначение

Система предназначена для автоматизации творческого процесса писателей и ворлдбилдеров: управление рукописями, создание и редактирование художественных текстов с типографикой ГОСТ, ведение базы знаний о персонажах, организациях, локациях, построение кастомных календарных систем, AI-ассистирование при написании текстов, экспорт в различные форматы.

### 2.2. Цели

| Цель                                                          | Критерий достижения                                                                                                |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Обеспечить единое рабочее пространство для писателя           | Все функции (редактор, сущности, таймлайн, AI) доступны в одном окне приложения без переключения между программами |
| Снизить временные затраты на поддержание консистентности мира | Время поиска информации о персонаже/событии не превышает 5 секунд через систему быстрого поиска                    |
| Автоматизировать типографическое оформление                   | Экспорт документа соответствует требованиям ГОСТ 7.32 без ручной правки                                            |
| Обеспечить автономную работу с AI                             | Локальные LLM-модели работают без подключения к интернету на машине разработчика                                   |

## Раздел 3. Характеристика объекта автоматизации

**Объект автоматизации:** творческий процесс подготовки художественных и академических текстов, включающий:

- Написание и структурирование рукописи (главы, тома, арки)
- Ведение справочника по миру (персонажи, организации, государства, магические системы)
- Построение хронологии событий в произвольных календарных системах
- Работа с AI-ассистентом для генерации идей, переписывания, анализа текста

**Условия эксплуатации:**

- Персональный компьютер разработчика
- ОС: Windows/Linux/macOS
- Оффлайн-режим (локальная БД SurrealDB + локальные LLM)
- Опционально: облачная синхронизация

## Раздел 4. Требования к системе

### 4.1. Требования к системе в целом

**Структура системы:**
Система имеет клиент-серверную архитектуру с локальным размещением:

- **Клиентская часть:** SPA-приложение (Vue 3 + TypeScript), встроенное в Tauri-оболочку
- **Серверная часть:** Rust-приложение (Tauri runtime) с hexagonal архитектурой
- **База данных:** SurrealDB (встроенная, локальная)
- **AI-движок:** llama.cpp (локальные GGUF-модели)

**Подсистемы:**

1. Подсистема управления рукописью (Manuscript)
2. Подсистема редактирования текстов (Editor / WordVibe)
3. Подсистема знаний и сущностей (Knowledge / Entities)
4. Подсистема календарей и таймлайна (Timeline / Calendars)
5. Подсистема AI-ассистирования (AI)
6. Подсистема экспорта и печати (Export)
7. Подсистема облачной синхронизации (Sync)
8. Подсистема настроек и кастомизации (Settings)

**Режимы функционирования:**

- Рабочий (редактирование, просмотр)
- AI-режим (генерация текста, чат с моделью)
- Режим экспорта (рендеринг в DOCX/PDF/EPUB)
- Режим синхронизации (обмен данными с облаком)

**Надёжность:**

- Автосохранение текста каждые 30 секунд
- Восстановление сессии после аварийного завершения
- Резервное копирование БД перед критическими операциями

**Безопасность:**

- Локальное хранение всех данных (нет утечки в интернет при работе с AI)
- Шифрование облачной синхронизации (если реализуется)

**Эргономика:**

- Тёмная/светлая тема
- Кастомизируемая типографика
- Горячие клавиши для всех частых операций
- Командная палитра (Ctrl+P) для быстрого доступа

## 💡 Как это использовать (практические советы)

**1. Не описывай каждый файл.** В ТЗ описываются **подсистемы** и **функции**, а не файловая структура. `ChapterTree.model.ts` — это деталь реализации, а не требование.

**2. Используй таблицы.** ГОСТ любит таблицы. Каждая функция = строка таблицы с описанием и критерием качества.

**3. Раздел 4 — самый жирный.** Здесь ты показываешь, что система сложная и продуманная. Описывай подсистемы по очереди.

**4. AI — отдельная подсистема.** Не размазывай AI по всем разделам. Выдели его как самостоятельный модуль с чёткими границами.

**5. Hexagonal architecture — плюс в карму.** Упомяни в разделе 4.1, что бэкенд построен по принципу чистой архитектуры (domain → ports → infrastructure → application). Это звучит солидно для курсача.

**6. Не забудь про тесты.** В разделе 5 и 6 обязательно укажи тестирование — это показывает зрелость подхода.

## Вариант А: Короткий (для ТЗ, раздел 4.3 — Информационное обеспечение)

> **Выбор СУБД.** В качестве системы управления базами данных используется встраиваемая документно-графовая СУБД SurrealDB. Выбор обусловлен следующими факторами:
>
> 1. **Автономность работы.** Приложение позиционируется как инструмент для одиночного автора, работающего в оффлайн-режиме. Использование клиент-серверной СУБД (PostgreSQL, MySQL) требовало бы развёртывания серверной инфраструктуры, что противоречит принципу автономности и невозможно при отсутствии источника финансирования (продукт распространяется под лицензией MIT).
>
> 2. **Сложность предметной области.** Проект содержит множественные связи различных типов: иерархические (том → арка → глава → текстовый блок), графовые (сущность ↔ сущность, сущность ↔ глава, сущность ↔ событие таймлайна), временные (событие ↔ календарь), семантические (чанки текста ↔ векторные эмбеддинги). Реализация подобной структуры в файловом хранилище (JSON) потребовала бы разработки собственной системы индексов, каскадного удаления, полнотекстового поиска (BM25), векторного поиска (HNSW) и контроля целостности связей — фактически, самописной СУБД.
>
> 3. **Требования к производительности.** При объёме данных, характерном для полноценного романа (3 тома × 4 арки × 20 глав × 8000 слов, 80+ сущностей, 1000+ чанков для RAG), файловый доступ с рекурсивным обходом и ручной индексацией обеспечивает недопустимо высокое время отклика на механических накопителях. Встроенная СУБД с оптимизированными индексами решает эту проблему.
>
> 4. **Наличие встроенных механизмов.** SurrealDB предоставляет из коробки: графовые связи (RELATION), события каскадного удаления (EVENT), полнотекстовый поиск с анализаторами (FULLTEXT ANALYZER BM25), векторные индексы (HNSW), ревизионирование (CHANGEFEED) и пользовательские функции (DEFINE FUNCTION). Перечисленные механизмы являются критически важными для реализации RAG, GraphRAG, версионирования и семантического поиска.

## Вариант Б: Развёрнутый (для пояснительной записки или если научрук упёрся)

### Обоснование выбора архитектуры хранения данных

#### 1. Отказ от многопользовательской модели

Приложение WorldWiki позиционируется как инструмент для **одиночного автора** (single-user desktop application). Переход к многопользовательской модели потребовал бы введения дополнительной предметной области — управления доступом, включающей:

- Гранулярную систему прав и ролей (владелец, редактор, читатель);
- Шифрование трафика между клиентом и сервером;
- Шифрование базы данных на стороне хостинга;
- Резервное копирование и отказоустойчивость инфраструктуры;
- Соблюдение требований 152-ФЗ «О персональных данных» при обработке пользовательской информации.

Перечисленные требования выходят за рамки целей курсового проекта и требуют отдельного финансирования (аренда серверов, SSL-сертификаты, аудит безопасности). Поскольку продукт распространяется под лицензией MIT и не предполагает монетизации, источники финансирования отсутствуют.

Кроме того, ключевое требование к продукту — **автономность**. В условиях нестабильного интернет-соединения (в том числе вынужденного отключения связи и введения белых списков) автор должен иметь возможность продолжать работу. Клиент-серверная архитектура с внешней БД делает это невозможным.

#### 2. Отказ от файлового хранения (JSON)

Рассмотрим типичный проект в системе: 3 тома, 20 глав в томе, 8000 слов в главе, 4 типа сущностей по 20 экземпляров каждого.

При файловом хранении каждая операция требует:

- **Идентификации объекта по ID.** ID уже является признаком реляционной модели: `text_block_id → chapter_id → volume_id`. Реализация навигации по такой иерархии в JSON требует либо полного сканирования директорий, либо ручного построения индексов.
- **Поддержки индексов.** Для глав — свой индекс, для блоков — свой, для сущностей — свой. Каждый индекс требует ручной синхронизации при CRUD-операциях.
- **Управления связями.** Сущности связаны с главами (участие), друг с другом (отношения), с событиями таймлайна (временная привязка), с чанками (семантический поиск). Каждая связь — это foreign key. При файловом хранении целостность связей обеспечивается вручную.
- **Поддержки RAG.** Чанки текста (не совпадающие с главами) требуют отдельных индексов. Поверх них накладывается векторный поиск (HNSW) и полнотекстовый (BM25). Реализация гибридного поиска вручную — задача уровня разработки собственной поисковой системы.
- **Версионирование.** Ревизии глав и сущностей требуют хранения снапшотов с возможностью отката. На JSON это реализуется через копирование файлов с метаданными — крайне неэффективно.

В результате файловое хранение превращается в **самописную СУБД**, лишённую оптимизаций, ACID-гарантий и проверенных механизмов восстановления.

#### 3. Обоснование выбора SurrealDB

Встраиваемая СУБД SurrealDB выбрана по следующим причинам:

| Требование               | Решение в SurrealDB                           | Реализация в JSON                         |
| ------------------------ | --------------------------------------------- | ----------------------------------------- |
| Иерархические связи      | `DEFINE TABLE ... TYPE RELATION` + `contains` | Ручной обход директорий                   |
| Графовые связи           | `entity_rel`, `appears_in`, `participates_in` | Ручные foreign keys, риск рассогласования |
| Каскадное удаление       | `DEFINE EVENT ... WHEN $event = "DELETE"`     | Ручная чистка зависимых файлов            |
| Полнотекстовый поиск     | `FULLTEXT ANALYZER like BM25`                 | Самописный инвертированный индекс         |
| Векторный поиск          | `HNSW DIMENSION ... DIST COSINE`              | Самописный ANN-индекс                     |
| Ревизионирование         | `CHANGEFEED 30d` + `entity_revisions`         | Копирование файлов                        |
| Пользовательские функции | `DEFINE FUNCTION`                             | Невозможно                                |
| Гибридный RAG            | BM25 + HNSW в одном запросе                   | Невозможно без промежуточного слоя        |
