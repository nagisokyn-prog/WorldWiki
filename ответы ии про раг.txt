Давай разберём твою ситуацию по полочкам. Сначала поищу актуальную инфу по ключевым компонентам твоей системы, а потом дам конкретную архитектуру под твой стек.
Вот как делают умные ребята. Твоя интуиция из диалога права: **большая модель не должна дёргать embedding-модель через tool calling**. Это архитектурный антипаттерн для твоего случая. Вместо этого retrieval — это слой middleware в твоём Rust-приложении, а LLM просто получает готовый контекст.

## 1. Ключевые факты про Nemotron (исправления из твоего диалога)

| Параметр | Факт |
|---|---|
| Размерность | **2048** (не 1024). Можно срезать до 1024/512, но после среза нужна повторная L2-нормализация  |
| Префиксы | `query:` для вопроса, `passage:` (или `document:`) для документов. NVIDIA предупреждает: неправильный `input_type` заметно портит accuracy  |
| Контекст | 32K токенов |
| Вес | ~550–650 МБ в Q4_K_M / ~2.6 GB в BF16 |
| Скорость | ~25–40 мс на CPU, ~5 мс на GPU для коротких запросов |

## 3. Почему именно так — разбор твоих вопросов

### "Как большая модель понимает, что ей нужна БД?"

**Ответ:** Она не понимает. Это не её работа.

Ты платишь за каждый токен и каждую миллисекунду latency в облако. Зачем платить за принятие решения "нужен ли поиск", если твой бэкенд может решить это математически за 8 мс?

Логика простая:
1. **Всегда** прогоняешь запрос через embedding-модель (она дешёвая и быстрая)
2. **Всегда** делаешь vector search
3. Если `max(similarity) < 0.65` — ничего релевантного нет, отправляешь чистый промпт
4. Если `max(similarity) > 0.75` — вставляешь найденные chunks в `<world_context>` и отправляешь

Так работают production RAG-системы: retrieval — это инфраструктура, а не агентское решение LLM.

### "Как связать llama-turboquant с Nemotron?"

Твой `llama-turboquant` (форк llama.cpp) умеет embedding-инференс:

```bash
# Запуск embedding-сервера
llama-server \
  -m nemotron-3-embed-1b-q4_k_m.gguf \
  --embedding \
  --pooling cls \
  -ub 8192 \
  -c 32768
```

Он поднимает OpenAI-compatible endpoint `/embedding`. Из Rust ты можешь ходить туда локально по `http://localhost:port/v1/embeddings`.

Но для desktop-приложения лучше **не поднимать HTTP-сервер**, а использовать llama.cpp как библиотеку через FFI или готовые Rust-биндинги (`llama-cpp-rs`). Тогда модель сидит в памяти процесса Tauri и отвечает за **25–40 мс** без оверхеда HTTP.

### "Модель в ОЗУ грузить — ок?"

Да, и это правильно. Но сделай lazy loading:

```
Tauri AppState
├── llm_runner: Option<Arc<Mutex<LlamaModel>>>  ← генеративная модель (если локальная)
├── embedder: Option<Arc<Mutex<Embedder>>>       ← Nemotron, резидентный
├── db: SurrealDB
└── ...
```

```rust
// Псевдокод для твоего runner.rs
impl Embedder {
    async fn embed_query(&self, text: &str) -> Vec<f32> {
        // Автоматически добавляем префикс
        let prefixed = format!("query: {}", text);
        // llama.cpp inference
        self.model.embed(&prefixed, Normalize::L2)
    }
    
    async fn embed_passage(&self, text: &str) -> Vec<f32> {
        let prefixed = format!("passage: {}", text);
        self.model.embed(&prefixed, Normalize::L2)
    }
}
```

Первая загрузка модели — при первом запросе, требующем retrieval. Дальше она висит в RAM. Если 30 минут не использовалась — unload.

## 4. Конкретика под твою БД (entities + SurrealDB)

У тебя в БД уже есть `embeddings.local` (HNSW 1024) и `embeddings.openai` (HNSW 1536). Но Nemotron-3 выдаёт **2048 dim**. Значит тебе нужен третий индекс:

```sql
DEFINE INDEX embeddings_nemotron ON entities FIELDS embeddings.nemotron HNSW DIMENSION 2048;
```

Или срезать до 1024 (с повторной нормализацией) и использовать существующий `embeddings.local`, но тогда теряешь accuracy.

### Chunking для больших entities

Твоя entity "Валтис" может быть на 20 страниц. Не делай один embedding на всю entity — сигнал размазывается.

```rust
struct EntityChunk {
    entity_id: String,
    chunk_index: u16,
    text: String,
    embedding: Vec<f32>,  // 2048 dim
}

// При сохранении entity:
// 1. Разбиваешь content на chunks (по ~512 токенов с overlap)
// 2. Каждый chunk: "passage: {chunk_text}"
// 3. Сохраняешь в отдельную таблицу entity_chunks
```

При retrieval находишь chunks, а `context_builder` группирует их обратно по `entity_id` и собирает контекст для LLM.

### Hybrid search (BM25 + Vector)

У тебя уже есть `name BM25` и `description BM25`. Используй оба:

```rust
async fn retrieve(query: &str, project_id: &str) -> Vec<Context> {
    // Параллельно:
    let vector_candidates = vector_search(query, project_id).await;  // Nemotron + HNSW
    let lexical_candidates = bm25_search(query, project_id).await;   // name + description
    
    // Объединяем, dedup по entity_id
    let merged = merge_and_dedup(vector_candidates, lexical_candidates);
    
    // Reranker (опционально, можно позже)
    // let ranked = rerank(query, merged).await;
    
    // Фильтруем по score
    merged.into_iter().filter(|c| c.score > 0.70).collect()
}
```

### Graph expansion (entity_rel)

Это самое мощное в твоей схеме. После semantic search:

```rust
// Нашли Валтиса и Элину через vector search
let seed_entities = vec!["Валтис", "Элина"];

// Достаём их связи из entity_rel
let relations = db.query("
    SELECT * FROM entity_rel 
    WHERE in IN $seeds OR out IN $seeds
").bind(("seeds", seed_entities)).await?;

// Добавляем связанные entities в контекст
// Валтис --[distrust]--> Элина (start_chapter: 17)
```

LLM получает не просто сырые тексты, а структурированный контекст:

```xml
<world_context>
<Entity name="Валтис" type="персонаж">
  <Description>Лорд Валтис — 4-й король Элении...</Description>
  <RelevantChunk>После осады Валтис потерял доверие к Элине...</RelevantChunk>
</Entity>

<Relation from="Валтис" to="Элина" type="distrust" strength="0.9">
  <Description>Перестал доверять после смерти Рейна</Description>
  <StartChapter>17</StartChapter>
</Relation>
</world_context>
```

Вот что вставляешь в system prompt (Claude/GPT/DeepSeek):


## 6. Итоговая схема для твоего runner.rs

```rust
// Псевдокод
pub async fn process_message(
    &self,
    user_msg: String,
    session: SessionContext,
) -> Result<Stream<Token>, Error> {
    
    // 1. Retrieval (всегда, но дёшево)
    let context = if should_skip_retrieval(&user_msg) {
        None  // "Привет", "спасибо", < 8 символов
    } else {
        let query_emb = self.embedder.embed_query(&user_msg).await?;
        let candidates = self.db.vector_search(&query_emb, &session.project_id).await?;
        
        // Hybrid: добавляем BM25
        let lexical = self.db.bm25_search(&user_msg, &session.project_id).await?;
        let merged = merge(candidates, lexical);
        
        // Graph expansion
        let with_relations = self.expand_graph(merged).await?;
        
        // Score gating
        if with_relations.max_score() < 0.65 {
            None
        } else {
            Some(self.context_builder.build(with_relations))
        }
    };
    
    // 2. LLM call (ровно 1 запрос в облако!)
    let prompt = build_prompt(user_msg, context, session);
    self.llm.generate(prompt).await
}
```

**Ключевые метрики:**
- **1 запрос** к облачной LLM (вместо 2–3 при tool calling)
- **~30 мс** на CPU для embedding
- **~5 мс** на vector search (HNSW)
- **0 токенов** потрачено на "решение искать или нет"

## 7. Что я бы НЕ делал (прямо из твоего диалога)

❌ **Tool calling для retrieval** — лишний round-trip, платишь за latency ×2 и токены на JSON-схему  
❌ **Заставлять LLM решать "нужна ли БД"** — это математически измеримая задача, не требующая нейросети  
❌ **Один embedding на всю entity** — размазывает сигнал  
❌ **1024 dim без перепроверки** — Nemotron-3 выдаёт 2048, срезать можно, но с осторожностью  
❌ **Грузить модель с диска на каждый запрос** — resident в RAM через `Arc<Mutex<>>` или lazy init  

---

**Вывод:** "Умные ребята" делают retrieval **middleware**, а не **tool**. Твой Nemotron — это не агент, которому LLM даёт задания. Это компрессор текста → вектор, который работает на уровне инфраструктуры приложения. LLM вообще не знает о его существовании.



Не убирать. Оставить оба пути — это не костыль, а **feature flags по уровням зрелости пользователя**.

Вот как выглядит нормальная архитектура, где tool calling и Auto-RAG сосуществуют:

## Почему оставлять tool calling — правильно

**BM25 по именам entities работает без нейросети вообще.** У тебя уже есть индексы `name BM25` и `description BM25`. Это 0.5 мс на запрос, не требует RAM под модель, не требует скачивания GGUF.

Поэтому даже пользователь **без Nemotron** получает базовый RAG:
- Пишет «Что Валтис думает об Элине?»
- BM25 находит entities по именам
- Контекст вставляется в промпт **автоматически**
- LLM отвечает с фактами

А tool calling остаётся для случаев, когда middleware не справилась:
- «Тот предатель из третьей главы» — BM25 не найдёт, embedding тоже может промахнуться
- LLM с tool `search_lore()` может сделать **переформулированный** поиск
- Или вообще пойти в веб, если у тебя есть `web_search` tool

## Три режима в настройках приложения

```rust
enum RetrievalStrategy {
    /// Для слабых ноутов и ленивых пользователей
    /// BM25 + tool calling. Нет локальной модели.
    CloudOnly,
    
    /// Для тех, кто скачал Nemotron
    /// Middleware делает semantic search, LLM не знает о БД
    LocalAutoRag,
    
    /// Золотая середина (рекомендую)
    /// BM25 всегда → Nemotron если есть → tools как fallback
    Hybrid,
}
```

### Режим CloudOnly (default)

```rust
// В runner.rs
async fn handle_cloud_only(&self, msg: &str) -> Result<Response> {
    // 1. Быстрый BM25 — почти бесплатно
    let quick_hits = self.db.bm25_search_names(msg).await?;
    
    let context = if quick_hits.max_score() > 0.75 {
        // Нашли точно по имени — вставляем сразу
        Some(self.build_context(quick_hits))
    } else {
        None
    };
    
    // 2. Отправляем LLM. Если контекста нет — дадим tools
    let tools = if context.is_none() {
        vec![self.search_lore_tool(), self.web_search_tool()]
    } else {
        vec![] // LLM уже видит контекст, пусть просто отвечает
    };
    
    self.llm.generate(msg, context, tools).await
}
```

### Режим LocalAutoRag

```rust
async fn handle_local_rag(&self, msg: &str) -> Result<Response> {
    // 1. BM25 (всегда)
    let lexical = self.db.bm25_search(msg).await?;
    
    // 2. Nemotron (только если загружен)
    let semantic = if let Some(emb) = &self.embedder {
        let vec = emb.embed_query(msg).await?;
        self.db.vector_search(&vec).await?
    } else {
        vec![]
    };
    
    // 3. Merge + rerank
    let candidates = merge(lexical, semantic);
    
    let context = if candidates.max_score() > 0.70 {
        Some(self.build_context(candidates))
    } else {
        None
    };
    
    // 4. LLM получает готовый промпт, tools не нужны для поиска лора
    // Но tools для веба/другого можно оставить
    self.llm.generate(msg, context, vec![]).await
}
```

### Режим Hybrid (рекомендую)

```rust
async fn handle_hybrid(&self, msg: &str) -> Result<Response> {
    // Layer 1: BM25 (всегда, дёшево)
    let mut context_parts = vec![];
    let lexical = self.db.bm25_search(msg).await?;
    if lexical.max_score() > 0.75 {
        context_parts.push(lexical);
    }
    
    // Layer 2: Nemotron (если включен)
    if let Some(emb) = &self.embedder {
        let vec = emb.embed_query(msg).await?;
        let semantic = self.db.vector_search(&vec).await?;
        if semantic.max_score() > 0.70 {
            context_parts.push(semantic);
        }
    }
    
    // Layer 3: Graph expansion (если нашли entities)
    if !context_parts.is_empty() {
        let relations = self.expand_graph(&context_parts).await?;
        context_parts.push(relations);
    }
    
    let context = if context_parts.is_empty() {
        None
    } else {
        Some(self.build_context(context_parts))
    };
    
    // Layer 4: LLM
    // Если контекст есть — LLM просто отвечает
    // Если контекста нет — даём tools, пусть сама решает
    let tools = if context.is_none() {
        vec![self.search_lore_tool()]
    } else {
        vec![]
    };
    
    self.llm.generate(msg, context, tools).await
}
```

## Tool calling куда деть

Оставь tools для **всего, что не является фактическим поиском по твоей БД**:

```rust
vec![
    // Этот tool можно вообще выпилить для пользователей с Auto-RAG
    // или оставить как "глубокий поиск" для сложных случаев
    Tool::search_lore(),
    
    // Этот точно оставляем — веб не заменить middleware
    Tool::web_search(),
    
    // Этот тоже оставляем
    Tool::generate_image(),
]
```

**Ключевой инсайт:** tool `search_lore()` не обязан уметь semantic search. Для облачных пользователей он может делать простой `SELECT WHERE name CONTAINS $term` — LLM сама сформулирует правильный запрос. А для локальных пользователей у тебя есть Nemotron, который делает это лучше и быстрее.

## Итог

**Не убирай tools.** Сделай слоистую систему:

1. **BM25** — всегда, бесплатно, не требует модели
2. **Nemotron** — опционально, для тех кто скачал
3. **Tool calling** — fallback, когда middleware не нашла ничего релевантного, или для веба/других интеграций

Тогда:
- Пользователь с Intel UHD и 4 GB RAM → BM25 + tools, всё работает
- Пользователь с RTX 4060 → полный Auto-RAG с графом и reranker
- Ты не поддерживаешь два разных приложения — один `runner.rs`, три режима в настройках

Это и есть "как делают умные ребята" — не выбирать между подходами, а **складывать их по уровням уверенности**.



Да. И вот тут как раз в том диалоге нейронка **слегка уехала не туда**.

Ты спрашиваешь не «как сделать RAG», а гораздо более интересную вещь:

> **как сделать так, чтобы большая модель сама решала: “мне сейчас нужны данные из локальной БД”, но при этом поиск выполнялся маленькой embedding-моделью, а не через tool call большой модели?**

И «умные ребята» обычно **не заставляют embedding-модель самой решать, нужен ли поиск**. Они разделяют это на несколько уровней.

### Главное: embedding-модель вообще не должна решать «нужна ли БД»

Она умеет примерно следующее:

```text
текст
  ↓
embedding model
  ↓
[0.12, -0.03, 0.87, ...]
```

То есть она отвечает на вопрос:

> «Насколько этот запрос похож на вот эти документы?»

А не:

> «Нужно ли нам сейчас обращаться к БД?»

И NVIDIA именно так описывает стандартный RAG pipeline: запрос превращается в embedding → по нему ищутся документы → найденный контекст передаётся LLM. ([NVIDIA Docs][1])

У тебя IDE для писателя. Поэтому я бы **вообще не заставлял Claude/GPT/что там выбрано заниматься retrieval**.

Схема:

```text
                         ┌──────────────┐
                         │   User msg   │
```

## Но тогда возникает твой главный вопрос

> А как понять, что сообщение требует БД?

Вот тут есть **три нормальных варианта**.

### Вариант №1 — всегда делать дешёвый retrieval

Это самый простой.

Каждое сообщение:

```text

        ↓

        ↓

        ↓
```

А:

```text

        ↓
Nemotron
        ↓
vector search
        ↓
0.91
        ↓
нашли lore
        ↓
LLM + lore
```

И **это не обязательно дорого**.

И вот здесь в предыдущем диалоге была важная ошибка: утверждение вроде

> «Nemotron будет работать 25–40 мс на любом CPU»

нельзя считать универсальной характеристикой.

Текущий `nvidia/nemotron-3-embed-1b` — действительно embedding-модель примерно 1.14B параметров, но NVIDIA указывает **2048-dimensional embeddings**, а не те 1024, которые были написаны в твоём тексте. У неё также есть отдельные режимы `query` и `passage`. ([NVIDIA Documentation][2])

Поэтому я бы не строил архитектуру вокруг красивых «5 мс».

# А ещё лучше — hybrid retrieval

Вот это уже действительно production-подход.

Не выбирать:

NVIDIA сама сейчас описывает NeMo Retriever как связку **embedding → vector search → reranking → generation**, то есть reranker является отдельным этапом, а не обязанностью основной LLM. ([NVIDIA Developer][3])

## Причём embedding-модель можно держать в RAM

Вот тут твоя первоначальная идея была абсолютно здравая.

**Не загружать модель на каждый запрос.**

Она должна быть отдельным resident-компонентом:

```text
Tauri process
│
├── AI runner
│
├── embedding service
│     └── Nemotron 1B
│
├── SurrealDB
│
└── cloud LLM client
```

Запустил приложение → embedding-модель загрузилась → дальше живёт.

А если пользователь вообще не пользуется функциями, которым нужен retrieval, можно сделать **lazy loading**:

```text
IDE startup
   ↓
Nemotron НЕ загружаем

первый запрос, требующий поиска
   ↓
load embedding model
   ↓
держим в RAM
```

И после некоторого idle timeout:

```text
30 мин без retrieval
       ↓
unload
       ↓
RAM освобождена
```

Это уже гораздо приятнее для ноутбуков.

# И ещё важный момент про Nemotron

В твоём файле написано:

> «1024 float-числа»

Это уже не стоит переносить в новую архитектуру как факт.

Для актуального `nemotron-3-embed-1b` NVIDIA указывает **2048 dimensions**. Причём NVIDIA отдельно поддерживает `float`, `int8`, `uint8`, `binary` и `ubinary`, что позволяет уменьшать память под сами вектора. ([NVIDIA Documentation][2])

И ещё важнее: `query` и `passage` действительно различаются — NVIDIA прямо предупреждает, что неправильный `input_type` заметно ухудшает retrieval accuracy. ([NVIDIA NIM API][4])

То есть идея из твоего диалога про:

```text
passage: ...
query: ...
```

**по сути правильная**, но конкретную реализацию надо делать согласно API/модели, а не вручную лепить эти префиксы наугад.

### И даже `id IN [...]` здесь не нужен

Это был мой особенно тупой пример.

Если у тебя сущности представлены в БД, то retrieval-слой должен работать с **естественным запросом**, а не требовать от пользователя идентификаторы.

Например, приложение само получает:


```text

        ↓
vector search
        ↓
top 20 candidates
```

Параллельно:

```text

 ↓
FTS/BM25
 ↓
top 20 candidates
```

Потом объединение:

```text

      ↓
dedup
      ↓
reranker
      ↓
top 5
```

И только **после этого** твой Rust-код знает, какие записи нужно достать полностью.

То есть условно:

```rust
let candidates = retrieval.search(&user_message).await?;
let context = context_builder.build(candidates).await?;
let response = llm.generate(user_message, context).await?;
```

А не:

```rust
// пользователь каким-то хуём должен знать ID
SELECT ... WHERE id IN (...)
```

Лучше:

```text
Entity: Валтис

  ├── chunk 1: внешность
  ├── chunk 2: детство
  ├── chunk 3: отношения с Элиной
  ├── chunk 4: участие в войне
  ├── chunk 5: убийство Рейна
  └── chunk 6: события после осады
```

Но **все эти chunks принадлежат одной entity**.

То есть retrieval возвращает:

```text
entity_id = Валтис
chunk_id = 17
score = 0.91
```

И context builder уже решает:

> «Мне нужен chunk 17, а возможно ещё соседние chunks этой entity».

---

## И тогда твоя система становится очень красивой

У тебя есть **одна универсальная сущность**:

```text
Entity
```

и поверх неё несколько механизмов:

```text
                    Entity Store
                         │
          ┌──────────────┼──────────────┐
          │              │              │
        exact          lexical       semantic
        lookup          search         search
          │              │              │
          └──────────────┼──────────────┘
                         ▼
                    reranking
                         │
                         ▼
                    context
                         │
                         ▼
                        LLM
```

Причём `exact lookup` тоже **внутренний**.

Если пользователь пишет:

> «Что Валтис думает об Элине?»

система может заметить, что в тексте встречаются имена существующих entities:

```text
Валтис → entity: abc123
Элина  → entity: def456
```

и добавить их в candidate pool.

Пользователь при этом ничего не вводил кроме обычного текста.

---

### И вот тут я бы ещё сильнее отделил две вещи

**Entity retrieval** и **document retrieval**.

Если у тебя вся информация пользователя живёт в entities, это не означает, что embedding должен быть:

```text
entity → один vector
```

Скорее:

```text
                 Entity
                   │
       ┌───────────┼───────────┐
       ▼           ▼           ▼
    metadata     chunks    relationships
       │           │           │
       ▼           ▼           ▼
     vector      vectors    vectors
```

Но все они имеют:

```text
entity_id
```

То есть vector search ищет **кусочки информации**, а приложение потом собирает их обратно в контекст сущностей.

---

И это уже хорошо сочетается с твоей первоначальной задумкой про Nemotron:

**Nemotron не является “умным агентом”.**

Он просто делает:

```text
текст → vector
```

А твой retrieval engine делает:

```text
vector
  ↓
найти похожие куски
  ↓
проверить score
  ↓
сгруппировать по entity
  ↓
собрать контекст
```

А большая модель получает уже:

```text
<world_context>

<Entity name="Валтис">
...
</Entity>

<Entity name="Элина">
...
</Entity>

</world_context>
```

И ей совершенно похуй, как ты это нашёл.

**Вот это, на мой взгляд, уже действительно нормальная архитектура именно под твою модель “пользователь сам создаёт любые сущности”.**


А, **теперь БД реально меняет картину**. Я посмотрел схему — и да, твоя идея с `entities` гораздо логичнее, чем я её сначала понял.

У тебя `entities` — действительно **универсальная пользовательская сущность**:

* `entity_type` — произвольный тип;
* `name`;
* `description`;
* `attributes` — гибкий объект;
* `tags`;
* `embeddings`;
* плюс отдельный граф `entity_rel`, где связи тоже имеют пользовательский `rel_type`.  

То есть условно пользователь может создать:

```text
"Валтис"
type = персонаж

"Серебряная чума"
type = болезнь

"Правило магии №7"
type = правило

"Зелёный чай"
type = предмет

"Как работает магия крови"
type = лор

"Странная хуйня из сна героя"
type = ???
```

И **система не должна заранее знать, что это такое**.

## И вот что особенно важно в твоей БД

Ты уже фактически подготовил инфраструктуру для того, что мы обсуждаем.

У `entities` уже есть **два разных semantic retrieval индекса**:

```text
embeddings.openai
    HNSW 1536

embeddings.local
    HNSW 1024
```

и отдельно:

```text
name → BM25
description → BM25
```



То есть тебе **не надо придумывать новую систему поиска сущностей**.

У тебя уже есть:

```text
                 entities
                     │
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
    name BM25    description    vector
                   BM25        local/OpenAI
```

И вот это, на мой взгляд, и надо использовать.

# Но я бы теперь сделал важное различие

Твоя БД содержит **не только entities**.

Есть ещё:

```text

```

и у нескольких из них тоже есть embeddings. Например `text_blocks` прямо помечены как предназначенные для семантики/RAG. 

Поэтому я бы не говорил:

Я бы говорил:

Например:

Это **мир проекта / содержимое книги**.

### 2. Conversation retrieval

Это история общения с AI. У тебя она тоже уже имеет embedding index. 

### 3. Agent memory

Отдельная память агента, тоже с embedding. 

### 4. Web knowledge

```text
web_cache
```

Вообще отдельный источник, который появляется после web search.

# И самое главное — теперь я понимаю, зачем тебе `entity_rel`

Вот здесь начинается действительно интересная часть.

Допустим запрос:

> «Почему Валтис перестал доверять Элине после смерти Рейна?»

Vector search находит:


Но у тебя между entities существует граф:

```text
Валтис
   │
   ├── [отношение] ──> Элина
   │
   └── [связь] ──────> Рейн
```

причём relation имеет:

```text
rel_type
description
strength
start_chapter
end_chapter

```

## Получается двухступенчатый retrieval

Например:

```text
User:
"Почему Валтис перестал доверять Элине?"
```

### Шаг 1 — semantic retrieval

Nemotron:

```text
query
 ↓
vector
 ↓
entities
 ↓
top candidates
```

Получили:

```text
Валтис      0.91
Элина       0.89
Предательство 0.84
Рейн        0.81
```

### Шаг 2 — graph expansion

Теперь retrieval engine говорит:

```text
нашли Валтиса
нашли Элину

→ посмотреть их связи

→ посмотреть связанные entities
```

Получаем:

```text
Валтис
 └── distrust → Элина
       ├── description: ...
       ├── start_chapter: 17
       └── related: Рейн
```

И вот **только это** идёт большой модели.

# Вот теперь твоя архитектура становится реально интересной

Потому что LLM не должна решать:

> «Дай-ка я вызову `get_entities()`».

Она получает:

```text
User query
     │
     ▼
Retrieval engine
     │
     ├── semantic
     ├── lexical
     ├── graph
     ├── session context
     └── memory
     │
     ▼
Relevant project context
     │
     ▼
LLM
```

То есть **LLM — генератор/рассуждатель, а retrieval engine — отдельный мозг доступа к знаниям проекта.**

И ещё одна вещь, которую я теперь вижу в твоей схеме:

у тебя уже есть `fn::get_rag_context`, но сейчас она вообще заточена только под **chapters + OpenAI embeddings**. 

То есть я бы **не стал поверх неё городить ещё один `entities search`**.

Я бы скорее переделал концепцию в отдельный retrieval service:

```rust
retrieve(
    project_id,
    query,
    session_context,
    retrieval_policy

```

где внутри уже:

```text

chapters
text_blocks
memory
chat history
graph relations
```

а наружу возвращается **единый набор найденного контекста**.

И вот **это**, судя по твоей БД, выглядит намного ближе к той архитектуре, которую ты на самом деле строишь.
